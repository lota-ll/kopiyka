# ADR-0006. Розділення лоадерів і парсерів; кілька карток в одному файлі

* Статус: прийнято
* Дата: 2026-08-03
* Замінює частину: ADR не скасовує попередні, уточнює архітектуру парсерів

## Контекст

Звірка з реальними виписками (серпень 2026) виявила:

* monobank віддає **CSV, окремий файл на кожну картку**; десятковий
  роздільник — крапка; порожні значення позначаються довгим тире `—`;
  колонки з номером картки немає;
* Приват24 віддає **XLSX, один файл на всі картки**; перший рядок —
  шапка «Історія операцій за період …»; є колонка «Картка», але вона
  порожня для частини операцій (комісії); MCC відсутній;
* користувач має чотири картки: дві monobank, дві Приват24.

Початковий контракт `parse(text: str)` для XLSX непридатний, а
припущення «один файл = один рахунок» хибне для Приват24.

## Рішення

**1. Два незалежні шари.**

```
файл (bytes)
   ├─ loaders/   → LoadedFile.rows: list[list[str]]   «як прочитати»
   └─ parsers/   → ParsedTransaction                   «як зрозуміти колонки»
```

Формат файлу і банк — незалежні осі. Якщо monobank перейде на XLSX,
зміниться лише детекція формату, парсер лишиться недоторканим.

**2. `ParsedTransaction.account_hint`.** Прив'язка до рахунку стає
властивістю *рядка*, а не *файлу*: останні чотири цифри картки
зіставляються з `accounts.account_ref`. Для monobank завжди `None` —
рахунок береться з параметра запиту.

**3. Невідома картка — помилка 422, а не автостворення рахунку.**

## Обґрунтування

Якби операції двох карток Приват24 потрапили в один рахунок, `dedup_hash`
(який включає `account_ref`) згорнув би дві однакові покупки з різних
карток в одну транзакцію. Дані зіпсувалися б тихо.

Автоматичне створення рахунку на невідому картку виглядає зручним, але
замаскувало б помилку «залив не той файл» — найімовірніший сценарій
плутанини при чотирьох картках.

## Наслідки

* Додано залежність `openpyxl` (+ `types-openpyxl` для mypy).
* Довге тире `—` внесено в `EMPTY_MARKERS` лоадера. Без цього нормалізатор
  грошей сприйняв би U+2014 як мінус і впав на порожньому числі.
* XLSX-суми приходять як `float` — конвертація йде через
  `Decimal(str(value))`, не `Decimal(value)`.
* XLSX-дати приходять як `datetime` — лоадер приводить їх до ISO.
* Помилки `openpyxl` (зокрема `BadZipFile`) обгортаються в `LoaderError`.
* Параметр ендпоінта імпорту перейменовано: `account_id` → `default_account_id`.
* Матчинг внутрішніх переказів піднято з тижня 5 у тиждень 2: за чотирьох
  карток кожен переказ потрапляє у виписки двічі, і без фільтрації
  аналітика витрат була б роздута.

## Доповнення (v0.2.2): операції без номера картки

Перевірка на реальних виписках виявила, що Приват24 не проставляє картку
для частини операцій — зокрема «Списання відсотків за використання
кредиту». Це рух за кредитним договором, а не карткова операція.

Віднесення таких рядків до рахунку за замовчуванням псувало б дані двічі:
сума потрапляла б не на той рахунок, а ланцюг залишків справжнього
рахунку розривався б.

**Рішення:** атрибуція за неперервністю ланцюга залишків
(`domain/attribution.py`). Операція відноситься до того рахунку, для якого
виконуються обидві рівності:

    залишок(операції)  == залишок(попередньої) + сума(операції)
    залишок(наступної) - сума(наступної) == залишок(операції)

Якщо ланцюг сходиться для кількох рахунків або для жодного — операція
лишається невизначеною і потрапляє у warnings. Вгадування тут гірше за
чесне «не знаю»: помилкова атрибуція мовчки псує аналітику, а невизначена
операція видно одразу.

Метод працює і для кредитних карток із від'ємним залишком — арифметика
та сама.
