# ADR-0002. Ізоляція тенантів через PostgreSQL RLS

* Статус: прийнято
* Дата: 2026-08-03

## Контекст

Система зберігає банківські виписки кількох домогосподарств. Витік між
тенантами — найтяжчий можливий дефект цього проєкту.

## Розглянуті варіанти

1. **Тільки фільтр у коді** (`WHERE household_id = ...`).
2. **Фільтр у коді + RLS у PostgreSQL.**
3. **Окрема БД на тенанта.**

## Рішення

Варіант 2 — оборона в глибину.

## Обґрунтування

Варіант 1 має один режим відмови, і він реалізується постійно: розробник
додає ендпоінт і забуває фільтр. Жодне ревʼю не ловить це стабільно.

RLS переносить інваріант із дисципліни розробника у двигун БД. Навіть
`SELECT * FROM transactions` без `WHERE` поверне лише рядки поточного
household.

Варіант 3 надмірний для очікуваного масштабу.

## Наслідки

* Застосунок підключається роллю `kopiyka_app` — **не власником таблиць**
  і без `BYPASSRLS`; інакше політики мовчки не діють.
* Обов'язковий `FORCE ROW LEVEL SECURITY`: власник таблиці інакше обходить
  політику.
* `SET LOCAL app.household_id` виконується **всередині транзакції**. Поза
  транзакцією при PgBouncer у transaction pooling параметр може загубитися
  або, гірше, застосуватися до чужого з'єднання.
* Міграції виконуються від власника (`KOPIYKA_MIGRATION_DATABASE_URL`),
  а не від ролі застосунку.
* Тести ізоляції в CI мають запускатися саме від `kopiyka_app`; під
  суперкористувачем вони зелені й безглузді.
